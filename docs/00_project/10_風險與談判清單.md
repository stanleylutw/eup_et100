## 🔴 P0 — 必須在 Kick-off 前解決

### 1. LTE 模組區域覆蓋不足（選型錯誤風險）

**PDF 依據**：P20 表格

| 目標市場 | 常用 LTE Band | EG800Q-EU 支援？ |
|----------|---------------|------------------|
| Taiwan | B1/3/8/28 (FDD)、B38/41 (TDD) | ⚠️ FDD 部分支援；TDD **完全不支援** |
| Vietnam | B1/3/5/7/8 (FDD) | ✅ 全支援 |
| Malaysia | B1/3/7/8 (FDD)、B40 (TDD) | ⚠️ TDD B40 **不支援** |
| Thailand | B1/3/5/8 (FDD)、B40 (TDD) | ⚠️ TDD B40 **不支援** |
| Indonesia | B1/3/5/8 (FDD)、B40 (TDD) | ⚠️ TDD B40 **不支援** |

**次要問題**：客戶需求 P04 寫「2G/3G/4G 頻段」，但 EG800Q 系列為純 LTE Cat 1 bis，**無 2G/3G fallback**。

**要求 Quectel 提供**：
- [ ] 逐國、逐電信商（Chunghwa/FarEasTone/Viettel/Vinaphone/Maxis/Celcom/AIS/DTAC/Telkomsel/Indosat）band mapping 表
- [ ] EG800Q-EU vs EG800Q-GL 對比（含 GL 版當前 project stage 與可交付時程）
- [ ] 明確聲明：是否放棄 2G/3G fallback？無網覆蓋區域行為為何？

### 2. 量產時程矛盾（商務紅線）

**PDF 依據**：
- P04：客戶預計量產時間 **2026 Q4**
- P47：Quectel 目標 MP **2027.03.31**（T0+9 個月）
- 差距 **約 6 個月**

**風險**：若 PAC/EUP 已對外承諾 2026 Q4 出貨，這份 schedule 直接失敗。認證週期（NCC 8 週、BSMI 8 週、MIC 6-8 週）尚未含入 T0-T9 時程。

**必談**：
- [ ] 若 T0 = 現在（2026.09），MP 落點 = 2027.06（未含認證 buffer） — 客戶端可接受？
- [ ] 若要壓到 2026Q4 MP，需並行做哪些事？額外費用？
- [ ] 認證期間是否可先出「pre-cert 版本」給 pilot 客戶？

### 3. 認證表與需求表不一致

**PDF 依據**：
- P04 客戶需求：Vietnam 認證 = **QCVN55、QCVN117**
- P49 Quectel 認證表：MIC 涵蓋 **QCVN 117:2023/BTTTT + QCVN 86:2025/BKHCN**
- **QCVN55 消失，被替換為 QCVN86**

**其他認證疑點**：
- MIC 註記「需實際進口商持證」— 誰是進口商？
- SIRIM 註記「需實際進口商持證」— 誰是進口商？
- CE (RED) 明確排除**戶外安全測試**與 **SAR 測試** — 車用不做 SAR OK 嗎？
- NBTC 說「泰國 DLT：中央控制盒不需執行，僅整車層級」— **DLT 責任在誰？**
- 認證項目 P53 Scope 竟然還寫「需客戶確認是否由 Quectel 負責認證」— **主體未定**

**合約附件要包含**：
- [ ] 每國每認證的：Owner / 持證方 / 樣品數 / 測項 / 重測責任 / SAR/outdoor safety 是否排除
- [ ] QCVN55 為何被拿掉？是否等同 QCVN86？
- [ ] 泰國 DLT 責任切分

## 🟠 P1 — 影響設計與 BOM 的關鍵疑慮

### 4. 備援電池續航與功耗算法有問題

**PDF 依據**：P14 功耗評估表本身有多處矛盾

| 疑點 | PDF 原文 | 問題 |
|------|----------|------|
| Discharge Efficiency 前後不一致 | 表頭寫 70%，下方 Actual Standby Time 列寫 "80% Discharge Efficiency" | 兩個數字**同頁矛盾** |
| LTE Start up Active Duration | **0 秒** | 開機不用時間？ |
| LTE Searching network Active Duration | **0 秒** | 弱訊號區搜網不吃電？ |
| Total 待機時間 | **4.2 小時** | 15 秒回報一次，車輛熄火隔夜就沒電 |
| 算式檢核 | 1554mWh × 0.7 / 371.8mW = 2.92h；× 0.8 = 3.34h | **都不是 4.2h**，算式本身有問題 |

**要求 Quectel 重出功耗表**：
- [ ] 統一 discharge efficiency 數字並說明依據
- [ ] LTE start up / searching / weak signal 三種情境的實測 duration
- [ ] 三組回報頻率情境：**15s / 60s / 300s** 各自續航時間
- [ ] GNSS **hot / warm / cold start** 分別的耗電
- [ ] 電池充放電 300 cycles 後衰減後的實際續航
- [ ] 明確定義「熄火後」的期望續航目標（例如 ≥7 天可回報）

### 5. 30 天本地儲存規格未定義

**PDF 依據**：
- P30：XM25QH256D = 256M-bit = **32 MB**
- P05 客戶需求：儲存至少 **30 天**資訊

**容量檢核**：
- 240 筆/小時 × 24h × 30 天 = **172,800 筆**
- 32MB ÷ 172,800 ≈ **194 bytes/筆**（未扣 wear leveling、bad block、韌體 config partition）
- 實際可用可能剩 20-24MB → **115-140 bytes/筆**

**單筆典型資料**：GNSS 位置 (~30B) + CAN J1939 payload (~50-100B, 可變) + RFID event + 溫度 4 點 (~16B) + timestamp + CRC/簽章 → **輕易超過 194 bytes**

**必須寫入驗收規格**：
- [ ] 單筆 payload 最大 size 上限
- [ ] 壓縮方式（有無）
- [ ] 循環覆寫策略（FIFO？優先保留事件？）
- [ ] 斷網重傳排序（LIFO？FIFO？）
- [ ] Flash wear leveling 演算法、預期壽命 cycle
- [ ] CAN 資料是否全存（若全存必爆）
- [ ] 240 筆/小時是否為固定值，事件觸發是否額外寫入

### 6. 內置天線效能不足且無實測交付

**PDF 依據**：
- P33：LTE 600-960MHz **效率 20-40%**（B5/B8 是 4G 主力頻段）
- P32-36 每頁都寫「**final performance will be determined based on actual debugging**」
- 機構 65×125×23mm 內塞 4 支天線 + LTE 模組 + GNSS + NFC 讀卡機

**風險**：
- LTE 低頻效率過低 → 郊區、山區、地下停車場斷訊
- 4 支天線相互干擾（尤其 NFC 13.56MHz 諧波、LTE 2.6GHz vs BT 2.4GHz）
- 全塑膠殼裝上車後 OTA 表現可能再打對折

**EVT 必交測試報告**：
- [ ] 各頻段 TRP/TIS（含 conducted + radiated）
- [ ] GNSS CN0 vs 商用參考機比較、TTFF（cold/warm/hot）
- [ ] NFC 讀距（4 種常見卡：MIFARE 1K、ICODE SLI、ISO14443A/B）
- [ ] BT RSSI @1m/5m/10m
- [ ] **整機裝殼並固定於車體後**的實車 OTA 報告（LTE + GNSS + BT）
- [ ] 各天線間 isolation 報告

## 🟡 P2 — 影響長期維護的合約條款

### 7. 軟體 SOW 條目太泛

**PDF 依據**：P44 / P45 只列功能名稱，無驗收標準

**必須改為可驗收條目**：
- [ ] **EUP 終端設備通訊協定**：完整規格書版本、conformance test 清單、封包欄位定義
- [ ] **OTA rollback**：觸發條件（開機失敗 N 次？CRC 錯誤？）、rollback 方案、失敗保護機制
- [ ] **OTA failure matrix**：斷網、掉電、韌體 corrupted、簽章驗證失敗、各種情境的 recovery
- [ ] **斷網重傳**：queue depth、優先順序、重連 backoff 策略、資料完整性驗證
- [ ] **CAN J1939**：支援的 PGN 白名單、bus load 上限、error frame 處理
- [ ] **BLE/RS232 設定權限**：加密方式、配對機制、預設密碼、設定黑名單
- [ ] **簽章金鑰管理**：金鑰產生、儲存、輪替、註銷方案；HSM 使用與否
- [ ] **Log schema**：欄位定義、版本控制、backward compatibility 承諾
- [ ] **伺服器 API**：MQTT topic / QoS / retain / LWT 定義、HTTPS endpoint 契約、責任分界

### 8. 交付物與 IP 歸屬未定義

**PDF 依據**：P53 只寫「Quectel can provide SCH(PDF version) and firmware」

**必須談判**：
- [ ] **完整 source code** 提供 or escrow（若供應商倒閉客戶還能維護？）
- [ ] **Build environment**：toolchain 版本、build script、reproducible build
- [ ] **Bootloader signing key**：所有權（客戶 vs Quectel）、備份、輪替
- [ ] **Debug tool 授權**：JTAG/SWD 存取權、log 解密工具
- [ ] **量產燒錄工具**：ATE spec、生產線工具轉移
- [ ] **RMA failure analysis SLA**：回應時間、報告格式、責任判定流程
- [ ] **Bugfix SLA**：P0/P1/P2 各級 SLA 時間、免費 bugfix 期間、後續 maintenance rate
- [ ] **License / IP ownership**：韌體是否有第三方 GPL/LGPL 元件？

### 9. NRE 分期付款與失敗條款

**PDF 依據**：P50 NRE 表

**問題**：
- R&D $117,500 只列 unit cost $4,700 一次，25 人月分散於 13 項，**個別項目單價完全不透明**
- 付款時間、驗收條件、失敗責任 → **全部未定義**

**建議付款結構**（按里程碑分期）：
- [ ] **T0 (Kick-off)**：20% = $25,000（含 SCH/PCB 初版設計）
- [ ] **EVT 驗收通過**：30% = $37,500（EVT 樣品+測試報告+HW/RF report 通過）
- [ ] **DVT 驗收通過**：25% = $31,250（DVT 樣品功能完整）
- [ ] **PVT 驗收通過**：15% = $18,750（PVT report + 認證送測完成）
- [ ] **MP + 首批出貨**：10% = $12,500

**失敗與變更條款**：
- [ ] EVT 若天線 TRP/TIS 未達 spec → **設計修改由 Quectel 負責**，客戶不再付費
- [ ] EVT 若功耗未達 spec → 同上
- [ ] EVT 若認證 band coverage 不足需換模組 → **NRE 增額由誰負責**（若源自需求誤解 vs 選型失誤）
- [ ] 客戶端規格變更 → change order 制度與費用計算方式
- [ ] Quectel 主動變更 BOM（例如 zero-defect 停產）→ **不加價、不延期**保證
